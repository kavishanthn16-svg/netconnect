# 234229X — TCP messaging (group + private chat)

Branch: `feature/234229x-messaging` (from `origin/development` @ `72fefd2`).
Owned paths: `server/chat/**`, `client/chat/**` and their tests. No shared/common/root/other-owner file was changed.

## What was built

| Class | Role |
| --- | --- |
| `server/chat/ChatMessageRouter` | Implements frozen `MessageRouter`. Group → every registered session once (sender included). Private → sender + recipient only. Adds UUID `messageId`, UTC `sentAt`, `scope`, `toUser` (private only). Validates text 1–2000 chars (blank rejected). Sends `ERROR` (`USER_OFFLINE`, `INVALID_REQUEST`, `NOT_AUTHENTICATED`) echoing the request id. One failing recipient never blocks the rest. Text is never logged. |
| `server/chat/ChatEnvelopeHandler` | Adapter for the session owner's read loop: `boolean handle(Session, Envelope)`. Consumes only `CHAT_GROUP_SEND` / `CHAT_PRIVATE_SEND`, returns `false` for everything else. Rejects malformed payloads and envelopes whose `sessionId` is not the connection's own. |
| `client/chat/ChatPane` | Self-contained JavaFX node: Group/Private switch, recipient box, message cards, 2000-char counter, status line. Sends on a background thread; all UI updates via `Platform.runLater`. |
| `client/chat/ChatSender` | Outbound interface the shell implements over its TLS connection. |
| `client/chat/ChatProtocol` | Builds `CHAT_*_SEND` envelopes, parses `CHAT_DELIVER`. |
| `client/chat/ChatConversationModel`, `ChatMessage` | Non-FX store: de-dup by `messageId`, group/private split, 1000-message cap. |

Network concept: TCP, reliable and ordered newline-delimited JSON over the control connection; server-side routing with no private-message leakage.

## Wiring (done by the owners of those modules, not by this branch)

Server (234106T / 234042R), in the per-connection read loop after authentication:

```java
ChatMessageRouter router = new ChatMessageRouter(sessionRegistry, controlGateway);
ChatEnvelopeHandler chat = new ChatEnvelopeHandler(router);
// for every decoded Envelope from an authenticated connection:
if (chat.handle(session, envelope)) return;   // chat consumed it
```

Client (234106T shell), on the FX thread when building the UI:

```java
ChatPane chatPane = new ChatPane(displayName, new ChatSender() {
    public void sendGroup(String text) throws Exception {
        connection.send(ChatProtocol.groupSend(sessionId, text));
    }
    public void sendPrivate(String toUser, String text) throws Exception {
        connection.send(ChatProtocol.privateSend(sessionId, toUser, text));
    }
});
chatTab.setContent(chatPane);
```

From the TLS dispatcher (any thread): `CHAT_DELIVER` → `chatPane.onDeliver(envelope)`; `USER_ROSTER` → `chatPane.onRoster(users)`;
`ERROR` for a chat request → `chatPane.onServerError(code, message)`; on disconnect → `chatPane.setSendingEnabled(false)` then `chatPane.close()`.
Use one pane per connection.

Decisions inside the frozen contract (flag in PR review if anyone disagrees): blank/whitespace-only text is rejected as `INVALID_REQUEST`; `toUser` is omitted from GROUP deliveries; recipient lookup is case-insensitive and `toUser` carries the canonical name; a private message to yourself is delivered once; a non-null envelope `sessionId` that differs from the connection's session is `NOT_AUTHENTICATED`.

## Tests (all in `mvn -B clean verify`)

| Test | Covers |
| --- | --- |
| `ChatMessageRouterTest` (17) | group once incl. sender, private no-leak, offline/unknown, invalid/oversized/boundary text, unauthenticated/stale session, UUID + UTC `sentAt`, failing recipient isolation, 16 KiB worst case |
| `ChatEnvelopeHandlerTest` (8) | routing, non-chat passthrough, malformed payloads, forged session id, request-id echo |
| `ChatTcpIntegrationTest` (4) | 5 real TCP clients × 20 = **100 messages** concurrently: exact delivery counts, no loss/duplication, no private leak, per-sender ordering; garbage and 20 KB lines don't kill a connection; offline error over TCP |
| `ChatProtocolAndModelTest` (9) | envelope field names, `CHAT_DELIVER` parsing, de-dup, history cap |
| `ChatPaneFxIsolatedTest` (1 → 8 scenarios) | real JavaFX toolkit in a child JVM: background send, local validation, view switching, failure display, off-thread delivery, disconnect |

The pane scenarios run in a child JVM because the discovery tests call `Platform.startup`/`Platform.exit` in the shared surefire JVM and a toolkit can start only once per process.
Not automated: the T11 "server killed mid-chat" UI behaviour and a multi-PC LAN run (needs the integrated shell).

## 2-minute demo (SRS §21)

1. Start the server; open clients Alice, Bobby, Carol (after shell/TLS integration).
2. Alice → Group: "Hello team". All three panes show it once, Alice's as "You".
3. Alice → Private → Bobby: "just for you". Bobby sees it; **Carol's pane shows nothing**.
4. Alice → Private → a user who has left: status shows "That user is offline".
5. Say: java.net sockets over TCP (reliable, ordered); server routes by session; private messages are delivered only to sender + recipient.
Before integration, the same flow is demonstrated by `ChatTcpIntegrationTest#thirdClientNeverSeesPrivateContent`.
